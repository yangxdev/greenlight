## diff-triage

### Problem

Developers are being handed far more AI-generated code than they can read, and say they no longer understand what changed. Two independent reports:

> "My coworkers are all fully AI pilled. As a consequence, every PR that comes my way for review is on average ~6k lines of diff. It's well established that even PRs an order of magnitude smaller than this are too big to be effectively reviewed. I'm still clinging to the idea that us humans should understand how the systems we are building work." (Lobsters Ask, "Surviving Code Reviews in the era of AI")

> "I was adding features at breakneck speed with Claude but I realized I have no clue how the new code works or what it changes or breaks." (Ask HN: "I'm going back to coding by hand", 62 points, 53 comments)

How often: both describe it as the normal state at work or in a side project, not a one-off. How many reviewers already use a manual workaround: unknown; the export has no comment text for either thread. Lobsters shows score 0 / 0 comments in the export, so engagement there is unmeasured.

### Target users

Reviewers and maintainers who receive large PRs (including from agents), and solo developers reviewing their own agent output. First 100: the two threads' participants, Lobsters and Hacker News readers, and r/ExperiencedDevs style communities (not in the export, so unverified).

### MVP in one day

- Single screen: paste a unified diff (`git diff` output or a GitHub `.diff` text), parsed in the browser. Nothing uploaded, no sign-up, no GitHub token.
- Summary strip: files changed, lines added/removed, and a plain warning when the diff is over a size threshold.
- Per-file list ordered as a reading plan, using fixed rules: config, dependency and lockfile changes first, then source files by size of change, then tests, then generated or vendored files grouped and collapsed.
- Flags per file from heuristics only: source changed with no test file touched in the same diff, large deletions, new dependencies, files renamed and edited.
- Tick-off checkboxes per file, so the reviewer sees how much is left; state kept in `localStorage`.
- "Copy review checklist" button producing Markdown for the PR comment.
- Success event for analytics: diffs pasted and files ticked per visit.

### Existing alternatives

- AI review bots and agents (the Product Hunt list this week has several coding-agent PR tools, for example Superset Mobile and Kilo Code, which let you review diffs from a phone): they add another opinion, they do not reduce the size of the reading job, and they need accounts or paid models. Whether a no-AI, paste-a-diff triage tool exists: unknown.
- GitHub's own PR view: file order is alphabetical, no size or risk ordering. Details beyond that: unknown from the signals.

### Explicit non-goals

- No AI summaries or paid model calls.
- No GitHub login, token or fetching of private repos.
- No inline comments or posting back to a PR.
- No judgement of whether the code is correct; it orders the reading, nothing more.
